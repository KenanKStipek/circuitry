- **`electricity-cel`: CEL evaluation for the electricity preview runner.**
  A new crate (`electricity/crates/electricity-cel`) wraps the `cel` crate
  behind Circuitry's own strict/non-strict layer, matching
  `core/cel_eval.py` rather than generic CEL behavior: the `Value` -> CEL
  type mapping (anything with no CEL counterpart, including a bare
  `datetime.date`, becomes `null`; a Python int too large for CEL's
  64-bit `int` raises instead); heterogeneous equality (`1 == true` is
  `false`, `int`/`uint`/`double` compare across subtype at the top level
  only — `1.0 == 1` is `true`, but the same cross-subtype comparison does
  **not** repeat inside a `list`/`map` or `in`'s own scan, matching
  `celpy`'s own, stricter, exact-type-inside-a-container
  `ListType`/`MapType.__eq__` rather than `cel`'s more permissive native
  one — `[1, 2] == [1.0, 2.0]` is `false`; a `bool` on the *left* of an
  `int`/`uint` is the one asymmetric exception, compared by value rather
  than raising, matching `celpy`'s own undecorated `BoolType`); `in`
  raising only for the type combinations that actually raise in `celpy`
  (an `int`/`uint`/`double` crossing a different numeric type, or a
  `list`/`map` against a non-`null`, differently-shaped value) and
  deciding `false` for every other mismatch, rather than raising on any
  mismatch at all, comparing every element of a nested `list`/`map`
  before deciding rather than stopping at the first one that raises (so
  the result never depends on a `HashMap`'s own unspecified iteration
  order); Python's own indexing (`list[i]`, and a bare `string`/`bytes`
  operand by character or by byte, something `cel`'s own `_[_]` has no
  indexer for at all), not `cel`'s native one — a negative `i` wraps
  from the end, a `bool` is `0`/`1`, a `double` always rejected, both
  inside `has()` and out; `in` over a `string`/`bytes` operand iterating
  its characters/bytes the same way `celpy`'s own `for c in container`
  does; a strict (non-cross-converting) map-key match, since `celpy`'s
  own `IntType`/`UintType.__eq__` raises on the other integer type as a
  key rather than finding the entry; numeric
  ordering raising for an `int` on the left compared against a different
  numeric type (matching `celpy`'s asymmetric `IntType`-only
  restriction), a `bool` tolerant of a number on either side the same
  way `celpy`'s own, undecorated `BoolType` is, a `NaN` resolving every
  comparison to `false` rather than raising, and an `int`/`double`
  comparison exact rather than rounding the `int` operand to the nearest
  representable `double` first; the absent-path convention for
  `if`/`while` mode (`evaluate_condition`) — an unset `state.` path makes
  the whole expression `false` with a logged warning, decided by walking
  the parse tree before evaluating, narrowed to what the expression
  actually reads when converting state, exempt for a `has(...)`-guarded
  path (`has(X)` rewritten, at parse time, into
  `!@not_strictly_false(__electricity_false(X))` — true exactly when `X`
  itself evaluates without raising, for any `X`: any expression root, a
  comprehension's own loop variable, a macro/function-call result, a
  failing index, or an argument that was never a field selection to
  begin with, none of them special-cased) or under `strict: true`; and
  `evaluate_expect`'s different rule — an unresolved `value`/`meta`/
  `state` path raises instead. The 4096-character cap and the empty-
  expression/strict-path errors reuse Circuitry's own wording word for
  word (Python's own `repr()`, not a bare quote-wrap); `matches()` uses
  the `regex` crate. A differential corpus, generated by actually
  calling Circuitry's real `evaluate_cel`/`evaluate_cel_expect`
  (`electricity/scripts/generate_cel_corpus.py`), is checked in and
  replayed by the crate's tests; CI regenerates it and fails if it
  drifts.

  Findings from that corpus are documented in the crate rather than
  reproduced: naive and aware date-times never actually diverge inside
  CEL — `cel-python` itself defaults a naive `datetime` to UTC the
  moment it is converted, so the naive/aware split is `Value`'s own
  (Rust-side) ordering, not a CEL-layer concern; a dict key with no CEL
  counterpart (a `float`, `None`, a bare `date` — all reachable from an
  ordinary YAML input file, not just data buried in `value`/`meta`) is
  dropped rather than collapsed into Python's single `null` key, which
  `cel`'s own map-key type cannot represent at all; a big int in
  `value`/`meta`/`state` for `evaluate_expect` raises a `CelError` here
  rather than reproducing either of the two different, uncaught-`ValueError`
  outcomes `core.tool`/`core.use` actually have for that case in Python
  (`CelError::is_overflow` lets a future caller pick one to match if that
  parity ever matters); and a `bool` map key against an `int`/`uint`
  lookup (or the reverse) doesn't reproduce `celpy`'s own asymmetry
  there (an `int`/`uint` probe finds a `bool`-keyed entry; a `bool`
  probe does not find an `int`/`uint`-keyed one), pinned by a Rust unit
  test rather than the differential corpus, which can't express an
  intentional non-match.
