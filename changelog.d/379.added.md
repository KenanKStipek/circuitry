- **`electricity-cel`: CEL evaluation for the electricity preview runner.**
  A new crate (`electricity/crates/electricity-cel`) wraps the `cel` crate
  behind Circuitry's own strict/non-strict layer, matching
  `core/cel_eval.py` rather than generic CEL behavior: the `Value` -> CEL
  type mapping (anything with no CEL counterpart, including a bare
  `datetime.date` and a Python int too large for `i64`, becomes `null`);
  heterogeneous equality (`1 == true` is `false`, `int`/`uint`/`double`
  compare across subtype); the absent-path convention for `if`/`while`
  mode (`evaluate_condition`) — an unset `state.` path makes the whole
  expression `false` with a logged warning, decided by walking the parse
  tree before evaluating, exempt for a `has(...)`-guarded path or under
  `strict: true`; and `evaluate_expect`'s different rule — an unresolved
  `value`/`meta`/`state` path raises instead. The 4096-character cap and
  the empty-expression error reuse Circuitry's own wording word for word;
  `matches()` uses the `regex` crate. A differential corpus, generated by
  actually calling Circuitry's real `evaluate_cel`/`evaluate_cel_expect`
  (`electricity/scripts/generate_cel_corpus.py`), is checked in and
  replayed by the crate's tests; CI regenerates it and fails if it
  drifts.

  Two findings from that corpus, both documented in the crate: naive and
  aware date-times never actually diverge inside CEL — `cel-python`
  itself defaults a naive `datetime` to UTC the moment it is converted,
  so the naive/aware split is `Value`'s own (Rust-side) ordering, not a
  CEL-layer concern; and the `cel` crate's own `has()` only guards the
  *last* segment of its argument, raising instead of resolving to `false`
  for a path missing two or more levels deep (`has(state.a.b)` when `a`
  itself is absent) — closed at the data level (ensuring every
  intermediate segment of a `has()` argument exists, as cel-python's own
  whole-chain `has()` would see it) rather than switching to `cel-core`.
