- **Reports reach runtime plugins and `cof tui`.** A `report` effect now
  fires an optional `on_report` hook on every loaded runtime plugin —
  `report`, a dict with the same fields as the `--events` report line minus
  its envelope: `ts`, `path`, `level`, `message`, then `data` or
  `data_truncated` past the 16 KiB compact-JSON limit. A plugin missing the
  hook keeps working unchanged, and a plugin that raises is logged without
  failing the run, the same contract `on_effect_start` already has. Reports
  reach plugins whether or not `--events` is set, from every entry point
  that loads runtime plugins (`cof run`, MCP, the SDK, `cof tui`, the
  scheduler and REST trigger). The built-in plugins that forward
  `on_effect_complete` forward reports too: `jsonl-file` and the pub/sub
  publishers (`kafka`/`rabbitmq`/`nats`) get a `report` event; OpenTelemetry
  and Honeycomb add a `report` span event on the run's own span; Sentry adds
  a breadcrumb; Datadog and Prometheus add a `level`-tagged counter
  (`circuitry.reports` / `circuitry_reports_total`); Loki and CloudWatch add
  a labelled log line; ClickHouse and SurrealDB add a row to their existing
  per-effect table. The SQL persistence plugins and the document/KV/object
  snapshot stores don't need the hook — a named report is already in the
  state snapshot they persist. `cof tui`'s Run view now shows each report in
  a run log, `▸ <message>` (the message's first line, capped at 120
  characters, warnings in the theme's warning colour), and tracks the
  latest one on the status line.
