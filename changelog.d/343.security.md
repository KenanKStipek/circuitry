- **A fetched document named by its cache path is now a limited document
  for its `runtime:` block too, not just capability consent.** #340 made a
  document whose resolved path (symlinks followed) lies inside a library
  source's own cache directory count as fetched content for capability
  consent, but a run of such a path still used `trust_document=True`, so
  its `runtime:` block (adapter endpoints, plugin settings) applied as if
  the host had written it — a library document run by *name* was already
  limited, and the cache path was a second, unguarded door to the exact
  same file. `circuitry.cli.runtime_shim.run()` now overrides
  `trust_document` back to `False` whenever `LibraryRegistry.is_cache_path`
  says the resolved path is a cache path, next to the classification #340
  already made there — so every surface built on it (CLI, TUI, SDK, MCP,
  REST) inherits the fix: the document's `runtime.adapters`, `runtime.plugins`
  and similar host-level keys are dropped the same way an untrusted
  library-name run drops them, even when a caller (the SDK's own default)
  passes `trust_document=True` for a path it did not actually choose. A
  `cof fetch -o file.yml` copy saved outside any configured source's cache
  is unaffected, still trusted per #284, as documented. See
  `docs/threat-model.md` §6.
