- **A generated document can no longer widen the shell allowlist or use any
  tool, and the check now runs at dispatch time, not only when the document
  is first compiled.** A reflector's plan, and a `use` whose `inline:` is
  rendered from state (e.g. `inline: "{{{prime.plan.value}}}"`), carried a
  `shell` effect's own `params.allowed_commands` and a `service` effect's
  `params.shell: true` at face value, and could invoke any tool provider at
  all — a `scripted` reply containing a `shell` effect ran whatever command
  it named, with no warning. A document whose own text already breaks a
  rule is still refused up front, before any of its effects run; the
  authoritative check now also runs right before every tool effect inside a
  generated document actually dispatches, on every attempt, against its
  final provider and params — after Mustache rendering and the
  `params_json` merge — so a value only known at dispatch time (a
  `params_json` overlay, a `{from: ...}` reference that only resolves to a
  disallowed value once rendered) is caught too; a refusal there fails that
  one attempt and is never retried.

  A generated `shell` effect's `allowed_commands` may only narrow the
  effective allowlist — the union of the host config's default/pinned
  commands and every literal `shell` effect's own `allowed_commands`
  already in the document that generated it — never widen past it. A
  generated `service` effect's `shell` is decided the same way the
  `service` plugin itself decides it, and a true value is refused outright;
  a `service` effect that starts a process without `shell: true` has its
  executable checked against the same allowlist, as a bare name — a path
  never counts as a member of it. `params_json` can never set
  `allowed_commands` or `shell` on any effect, generated or not. A
  generated document may use only the tool providers the document that
  generated it already uses itself, statically, plus whatever the
  generating `use`/`reflector` effect's own literal `allow_tools:` field
  adds — and that allowance is inherited: a document nested inside an
  already-generated one is generated too, including a `use:
  {path:}`/`ref:`/`orchestration:` child, which no longer gets a fresh
  ceiling of its own just because it names a separate file; its own
  `allow_tools:` can never grant anything beyond what the enclosing
  document was itself allowed. A decomposition plan runs with the enclosing
  context's own limits when it already has any; otherwise with the document
  it serves's own providers plus a fixed set of side-effect-free data tools
  it has no generating effect to carry an `allow_tools:` for (`json`,
  `regex`, `math`, `cel`, `clock`, `base64`, `hex`, `uuid`,
  `validate_yaml`) — `csv` and `hash` are deliberately not in that set, since
  both can read an arbitrary local file by path. An author-written
  `inline:` whose structure is literal, with only scalar values templated
  in, is unaffected — only a document whose structure only exists because
  it was rendered is held to this, and a rendered value at a
  security-sensitive field (including a nested `inline:`, `path:`, `ref:`
  or `orchestration:`) counts as generated even inside an otherwise-literal
  structure.

  If your own reflector's or `use` effect's plan already uses a tool its
  document doesn't otherwise use, add that provider to its `allow_tools:`
  list to keep it working. If a generated `shell` effect ran a command
  outside the default allowlist, either add the command to a literal
  `shell` effect's `allowed_commands` somewhere in the document that
  generates the plan, or pin it host-wide via
  `runtime.plugins.shell.allowed_commands`. If a decomposition plan's own
  merge step used `csv` or `hash` with `from_path`, or any other tool
  outside the fixed safe set, move that step to the document the plan
  serves instead (so the plan inherits it statically) or reshape the merge
  to use one of the safe tools.

  Both engines apply the identical rule and the same refusal text. See
  `docs/threat-model.md`'s "Generated documents" section and the
  orchestration reference's "Generated documents and tools".
