- **A generated document can no longer widen the shell allowlist or use any
  tool.** A reflector's plan, and a `use` whose `inline:` is rendered from
  state (e.g. `inline: "{{{prime.plan.value}}}"`), carried a `shell` effect's
  own `params.allowed_commands` and a `service` effect's `params.shell: true`
  at face value, and could invoke any tool provider at all — a `scripted`
  reply containing a `shell` effect ran whatever command it named, with no
  warning. Both are now refused up front, before any of the generated
  document's effects run: its `allowed_commands`/`shell: true` are never
  honoured, and it may use only the tool providers the document that
  generated it already uses itself, statically, plus whatever the
  generating `use`/`reflector` effect's own new, literal `allow_tools:`
  field adds. A decomposition plan follows the shell-allowlist rule the same
  way, but has no `allow_tools:` of its own (no generating effect to carry
  one). An author-written `inline:` whose structure is literal, with only
  scalar values templated in, is unaffected — only a document whose
  structure only exists because it was rendered is held to this. If your own
  reflector's plan already uses a tool its document doesn't otherwise use,
  add that provider to the reflector's (or the `use` effect's) `allow_tools:`
  list to keep it working. Both engines apply the identical rule and the
  same refusal text. See `docs/threat-model.md`'s "Generated documents"
  section and the orchestration reference's "Generated documents and tools".
