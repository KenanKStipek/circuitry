- **Capability consent (#275) now closes every surface, not just `cof
  run`.** A remote (refreshable, e.g. `github`) library source run by bare
  name resolved from the TUI's Library view ("run this entry" and the Runs
  view's replay of a stashed run) now carries the same whole-document
  capability gate `cof run hub/entry` applies, instead of reaching the
  resolved path without it; neither ever prompts, so an unconsented entry
  refuses with the same message a script or CI run gets.
  `circuitry.api.run_orchestration`/`run_shared_orchestration` take a new
  `allow_capabilities=[...]` parameter — the embedding program's own,
  never-persisted consent for one call, since it is the host deciding what
  runs. The MCP server's `run_orchestration` tool resolves a bare
  orchestration name against the same library registry `cof run` does and
  applies the identical gate; neither it nor the REST trigger exposes any
  field a caller can use to grant capabilities on their own behalf — only a
  document whose digest was already consented via `cof trust` runs. A
  `use: ref:` child reached from a REST- or scheduler-run, path-trusted
  top-level document (#284) stays independently gated either way, unaffected
  by any of the above. See `docs/threat-model.md` §9.
