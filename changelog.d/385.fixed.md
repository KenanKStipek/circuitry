- **Ctrl-C, SIGTERM or SIGHUP could be ignored until a running tree-flow branch or parallel-loop pass finished on its own, instead of stopping it promptly.** POSIX can deliver a signal to any thread that doesn't block it, not necessarily the main thread; a tree-flow `dynamic`/parallel `loop` waited for its branches via an unbounded `as_completed()`, so if the signal landed on a branch's own worker thread rather than the main thread, the pending Python-level handler was never run until that worker returned from its own blocking wait — for as long as the branch's own work took, up to the full duration of a long-running step. Investigating #385's load-flakiness report (one real CI failure, reproduced locally with a stack dump showing the main thread parked in a lock wait and the worker still blocked reading a child's pipe) found this, not scheduling starvation, as the actual cause. `core.dynamic`/`core.loop` now poll for completion instead of blocking indefinitely, so a pending signal is noticed within a fraction of a second regardless of which thread it reached; their cancellation path also gives an already-killed branch a bounded grace period to actually unwind before the run's own cleanup clears the cancellation flag, closing a second, narrower race the fix for the first one would otherwise have opened. `tests/cli/test_run_sighup.py` and `tests/cli/test_run_cancel_parallel.py`'s stop-promptness bound is now derived from the branch's own sleep length rather than a literal, and every timeout there now dumps the child's stdout/stderr and a stack trace of every thread instead of a bare `TimeoutExpired`, so a future failure is diagnosable from the CI log alone.
