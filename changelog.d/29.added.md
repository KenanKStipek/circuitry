- **Effect enable/disable semantics — `effects.<path>.enabled: false`.** A profile can switch any named effect off for a single run. A disabled effect is not executed; its node is written as `{value: null, meta: {disabled: true, created_at, completed_at}}` — deliberately the shape `on_error: skip` leaves behind, so downstream handling is uniform — and `on_effect_complete` still fires, so observability sees the skip rather than a gap. Disabling a container (`dynamic`/`loop`/`conditional`/`reflector`) disables its whole subtree; a disabled `loop` `collect` target is omitted from `collected` rather than padding it with nulls; templates referencing a disabled node render empty and CEL conditions that test for a value evaluate `False`. A conditional's `if` and a loop's `while` are conditions, not effects: targeting `<name>.if` / `<name>.while` / `<name>.condition` fails profile validation with an error naming the container to disable instead. The flagship use is turning agentic planning off for a run (`my_reflector: {enabled: false}`). Runs without `--profile` are unaffected — `enabled` is never set from orchestration YAML. See [Disabling Effects](docs/orchestration-reference.md#disabling-effects).
