- **Tool timeouts actually bound a tool.** A sub-second `timeout_ms`
  (e.g. `500`) used to floor to a 0-second timeout — `subprocess.run` failed
  instantly, curl's `--max-time 0` meant *no* limit, and `urlopen(timeout=0)`
  failed instantly too, three different wrong behaviors depending on the
  plugin. It now rounds up to at least one second. Tools also no longer
  inherit the run's LLM adapter timeout (`runtime.adapters.<name>.timeout_seconds`,
  default 120s): they get their own budget, `runtime.tools.timeout_seconds`
  in config, defaulting to 300s and set independently of whichever adapter
  the run happens to use.
- **`python_eval` can no longer hang a run forever.** Its RestrictedPython
  sandbox ran in-process with no way to interrupt a tight loop
  (`while True: pass`) or runaway allocation from the outside, so
  `timeout_ms` had no effect on it. It now runs in a forked child process
  with the same compile-time guards as before, killed on overrun (wall-clock
  deadline, plus best-effort `RLIMIT_CPU`/`RLIMIT_AS` where the platform
  actually enforces them) with a clear timeout error. `rss`, `wikipedia`,
  `discord`, and `web_fetch` — the other tool plugins that do unbounded
  network work and previously discarded the budget entirely — now honor it
  too; see the `tool` effect's Timeout section in the orchestration
  reference for the full list of which plugins do and don't.
