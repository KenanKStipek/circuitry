- **A first Ctrl-C/SIGTERM/SIGHUP landing at exactly the wrong instant during a tree-flow `dynamic`/parallel `loop`'s own branch bookkeeping could deadlock the run instead of cancelling it.** A handful of `concurrent.futures` calls on the main thread (registering a branch's completion callback, cancelling one not yet started, growing the worker pool) briefly hold a `Future`/executor lock that is itself a pure-Python `threading.Condition` — a signal's handler raising at the exact point that lock was about to be released could leave it held forever, wedging the worker thread that needed it next and hanging the run rather than stopping it. The handler now defers a first signal's exception during those few calls instead, letting the lock release normally and raising it immediately afterward — the token's flag is still set and every tracked process still killed at once either way, only the exception that unwinds the run's own call stack was ever delayed. The one unbounded wait on the main thread's own poll loop (`as_completed_promptly`) no longer uses a private lock-backed `Event` at all, closing the same exposure there outright rather than deferring around it. A related, separately-timed bug could also leave a branch running past cancellation: a signal landing on the main thread while it was still inside `ThreadPoolExecutor.submit` itself, before that branch's own future was ever recorded anywhere the cancel path looks, left nothing waiting for (or able to cancel) a branch the pool had already started running — the run still reported cancellation and exited promptly, but that one branch kept going, past the point its next step should have been stopped. Submitting a branch and recording its future now happen inside the same deferred region, so a signal landing at that exact point can no longer separate the two. The cancel path's own wait for an already-running branch to finish is covered by that same deferred region too, so a first signal landing during that wait can no longer cut it short and let the run report cancellation before every branch the kill couldn't reach has actually stopped. The cancellation token's own internal lock is covered as well: a first signal landing on the main thread while it briefly held that lock could previously leave a second Ctrl-C/SIGTERM unable to end the process immediately, as intended.
