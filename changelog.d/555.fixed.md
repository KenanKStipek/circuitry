- **A first Ctrl-C/SIGTERM/SIGHUP landing at exactly the wrong instant during a tree-flow `dynamic`/parallel `loop`'s own branch bookkeeping could deadlock the run instead of cancelling it.** A handful of `concurrent.futures` calls on the main thread (registering a branch's completion callback, cancelling one not yet started, growing the worker pool) briefly hold a `Future`/executor lock that is itself a pure-Python `threading.Condition` — a signal's handler raising at the exact point that lock was about to be released could leave it held forever, wedging the worker thread that needed it next and hanging the run rather than stopping it. The handler now defers a first signal's exception during those few calls instead, letting the lock release normally and raising it immediately afterward — the token's flag is still set and every tracked process still killed at once either way, only the exception that unwinds the run's own call stack was ever delayed. The one unbounded wait on the main thread's own poll loop (`as_completed_promptly`) no longer uses a private lock-backed `Event` at all, closing the same exposure there outright rather than deferring around it.
