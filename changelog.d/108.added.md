- **The complexity router now picks the model.** With `runtime.complexity.routing.enabled: true`, each prompt effect's score resolves through the band table and that band's `model` is what dispatches — recorded on the node as `meta.model` with `meta.model_reason: router`, alongside the `meta.complexity.band` that explains it, and on the run as `sources["model"] == "router"`. The substitution happens at the single place a model is resolved (`resolved_model = defn.model or run_default` in `core/prompt.py`), so a routed model is the default model for the `provider`/`provider_fallbacks` attempt chain exactly as a hand-written `model:` would be. Model names pass through untouched — tier names for the `cyberdiner` adapter, real model names for local ones. Explicit choices always win: a per-effect `model:`, a profile effect override, and `--model` each short-circuit the router, which still records the band it declined to apply so a run can say what routing *would* have picked; `respect_explicit: false` is the documented opt-out that lets the router decide for every scored effect. A band table is now a sufficient model configuration on its own — with routing on and no `--model`/orchestration `model:`/`default_model`, the catch-all band becomes the run default instead of the run failing with "no model resolved". With routing disabled, model selection is byte-identical to before. Runnable demo in `docs/examples/routing/`.
