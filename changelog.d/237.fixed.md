- **MCP `RunManager` quiescence is event-based, not time-based.** `start_run` no longer guesses "settled" from a fixed debounce window — a `flow: tree` loop or a parallel `dynamic` now tells the run manager exactly how many branches it is about to dispatch before any of them start, so `start_run` waits for a real signal (all expected branches registered, or the run went terminal) instead of racing a scheduling delay. `submit_response` now waits specifically for the answered prompt id to leave `pending_prompts` (or the run to go terminal), so a client re-reading state can never see the prompt it just answered as still current.
- **The branch-count signal now reaches a `flow: tree` nested inside another tree branch or a `use:` child**, accumulates across multiple dispatches instead of overwriting, is bounded by `max_concurrency` (the real ceiling on how many branches can ever be concurrently pending, not the total item count), and is lowered again as each dispatched branch finishes — including one that never registers a prompt at all (a tool-only branch, a `when:` skip). `submit_response` also now waits for the *next* settle point after the answered prompt is popped, not just the pop itself, so a chained prompt effect's reply is already visible in the return rather than requiring a client-side poll.
