- **Capability consent for a document that is not your own.** A
  `cof run-library`/`run_shared_orchestration` asset, a remote (refreshable,
  e.g. `github`) library source run by bare name, or any `use: ref:` child
  (reached from *any* document, trusted or not), now needs an explicit yes
  before its `shell`, `python_eval`, filesystem-write, or network tool
  effects run, the first time. `cof fetch` writing a file to disk, then a
  later `cof run ./that-file.yml`, stays a run by path and is never gated
  this way. Every bundled tool plugin is tagged with what it can do
  (`circuitry.plugins.capabilities.PLUGIN_CAPABILITIES`); before such a
  document runs, Circuitry works out statically which of the four
  capabilities its tool effects (and reachable `use` children) need, and an
  interactive `cof run`/`cof run-library` lists them and asks y/N. Anything
  else — MCP, REST, CI, no TTY — refuses outright, naming `cof trust
  <document>` (extended to accept a `.yml`/`.yaml` path, not just a project
  config) and a scripted/CI `--allow-capabilities shell,network,...` escape
  hatch that is never persisted. A yes is recorded by the document's own
  content digest in the same store `cof trust` keeps project-config trust in
  (`~/.config/circuitry/trusted.json`); an edited document asks again. A
  generated reflector/decomposition plan is held to the enclosing document's
  own consented capabilities, never its own prompt. A document named by path
  with no `use: ref:` is unaffected — naming it is still the decision to run
  it. See `docs/threat-model.md` §9.
