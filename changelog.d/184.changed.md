- **CEL expressions now fail loud instead of silently meaning `false`.** `cof check` parses every `mode: cel` expression at compile time and rejects what the evaluator cannot run — `!` negation, `has()`, the `.filter()`/`.map()`/`.all()`/`.exists()`/`.exists_one()` macros, comprehensions and the ternary `? :` — naming the effect and the expression (`CEL expression at 'prime.effects[0]' (effect 'gate'): CEL negation '!' is not supported yet; write '== false' instead.`), alongside the existing `state.*` namespace and 4096-character guards. At run time a translation, parse or evaluation failure raises a typed `CelEvaluationError` carrying the expression and its cause: the conditional (or loop `while`) records it on the effect's `meta.error` and the run finishes `ok=False`, the same shape a failing tool effect has, rather than quietly taking the `else` branch. `on_error: continue` still falls through to `else` — now as an explicit opt-in, with the error recorded. Reading *unset* state stays false and is not an error: a `state.` path that is missing or resolves through `null` makes the whole expression `false` by rule (decided before evaluation and logged with the offending path), so a disabled node's downstream condition still takes `else`; unlike the old error-swallowing, this now also covers negative tests — `state.prime.goal.value != ""` against an unset value is `false`, not `true`. A loop `while` condition that errors under `on_error: break`/`continue` terminates the loop with the new reason `condition_error` instead of spinning to `max_iterations`.
