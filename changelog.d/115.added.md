- **Runtime decomposition.** With `runtime.complexity.decomposition` enabled, a
  prompt effect whose complexity score strictly exceeds `threshold` is no longer
  dispatched as one over-complex call: the bundled planner (`agents/decompose`)
  runs in an isolated store, its emitted orchestration is validated (schema,
  chunk budget, merge contract) before anything runs, and the validated fan-out
  executes as a state-isolated child — same cycle guard and namespaced
  live-observability as a `use` child — with the merged result written back at
  the *original* effect's state path, so downstream `{{prime.<name>.value}}`
  references resolve unchanged. Recursion is bounded by `max_depth` (threaded
  through nested decompositions; at the ceiling the effect routes up to the
  routing table's catch-all model, or runs as-is when routing is off), and the
  attempt is recorded at `meta.decomposition` (outcome, depth, chunk count, the
  plan). Planner failure, an invalid plan, and child execution failure are
  governed by `on_failure`: `route_up` (default) falls back to running the
  original prompt — so a decomposition attempt can never turn a working run into
  a failed one — and `fail` propagates; no failure path leaves partial state at
  the original path.
