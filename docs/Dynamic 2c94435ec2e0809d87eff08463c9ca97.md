# Dynamic

A **Dynamic** is a named execution structure in Circuitry and is modeled as a monadic computation.

A Dynamic composes Prompts, Conditionals, Loops, and other Dynamics into a single executable unit. It defines **how execution occurs**, aggregates execution metadata, and produces a collection of Effects that are recorded in runtime state.

Dynamics do not plan, reason, or decide what should happen next. They only execute the effects they explicitly define.

---

## **Conceptual Definition**

A Dynamic is responsible for:

- structuring execution
- declaring control flow topology
- aggregating results and metadata
- recording execution outcomes to state

A Dynamic defines **how execution proceeds**, not **why execution occurs**.

All reasoning, intent, or planning must be expressed explicitly via Prompts, Conditionals, Loops, or external planning components.

---

## **Dynamic Definition (DOL)**

A Dynamic is declared declaratively in the orchestration domain object language.

### **Required Fields**

```
type: dynamic
name: string
flow: string
effects: array
```

Each item in effects must be one of:

- prompt
- dynamic
- conditional
- loop

---

### **Optional Fields**

```
description?: string

# Concurrency controls
max_concurrency?: number

# Error behavior
stop_on_error?: boolean
on_error?: string      # fail | continue | skip

# Metadata and annotations
labels?: object
```

---

### **Validation Rules**

- type must be "dynamic".
- name must be unique within its parent scope.
- effects must be a non-empty array.
- flow must resolve to a supported control flow model.
- All child effects must be valid DOL nodes.
- Execution order is determined by flow, not by array semantics.

---

## **Effects**

- **effects**
    
    A collection of executable effects.
    

Each effect is one of:

- a Prompt
- a Conditional
- a Loop
- another Dynamic

Effects are executed under a **shared effective execution context** derived from:

- the current state
- inherited values from the parent Dynamic

Effects are a **collection**, not an ordered sequence. Ordering, concurrency, and execution behavior are determined solely by the Dynamic’s declared control flow model.

---

## **Control Flow Models**

A Dynamic declares its execution topology using the flow field.

Control flow models are **structural**, not semantic. Certain values are treated as **aliases** and normalize to the same runtime behavior.

### **Sequential Execution**

**Canonical:** chain

**Aliases:** chain_of_thought, cot

Effects are executed sequentially in declared order. Each effect observes the evolving state produced by all prior effects.

Aliases indicate that intermediate reasoning steps are intentionally modeled and persisted, but they do not alter execution behavior.

```
flow: chain
# or
flow: chain_of_thought
# or
flow: cot
```

---

### **Parallel Execution**

**Canonical:** tree

**Aliases:** tree_of_thought, tot

Effects are executed concurrently using structured or bounded concurrency. Each effect observes the same input state snapshot and produces independent effects.

Aliases signal that branches represent alternative reasoning paths, but they do not introduce implicit pruning, evaluation, or selection.

```
flow: tree
# or
flow: tree_of_thought
# or
flow: tot
```

---

### **Normalization Rules**

At runtime:

- chain_of_thought and cot normalize to chain
- tree_of_thought and tot normalize to tree

Aliases exist for readability, documentation, and LLM guidance only.

---

## **Concurrency Controls**

- **max_concurrency**
    
    Limits worker count for bounded concurrency strategies such as tree.
    
    If unspecified, the runtime applies a conservative default.
    

---

## **Error Behavior**

- **stop_on_error**
    
    Determines whether the Dynamic fails fast when an Effect fails.
    
- **on_error**
    
    Determines how the Dynamic behaves when encountering an error, such as failing execution or continuing while recording error metadata.
    

---

## **Monad Semantics**

A Dynamic represents a computation of the form:

```
Dynamic : State → (State, Effects)
```

Where:

- **State** is read-only input and append-only output
- **Effects** is the collection of execution results produced by child effects
- Each Effect contains its own value and metadata

A Dynamic produces **no direct value**. Its result is the collection of Effects it records.

This structure enables predictable composition, deterministic execution, and full auditability.

---

## **Execution Lifecycle**

When executed, a Dynamic:

1. Builds an effective execution context from inherited values and current state.
2. Executes its effects according to the declared control flow model.
3. Applies concurrency and error-handling rules.
4. Records all Effects produced by execution.
5. Aggregates execution metadata across all descendant effects.
6. Writes a single Dynamic execution record to runtime state.

---

## **State Writes**

A Dynamic writes a single Dynamic Effect to runtime state under a deterministic path derived from its name and parent scope.

Each Dynamic record includes:

- **effects** — the collection of Effects produced by execution
- **meta** — aggregated execution metadata

Dynamics do not mutate domain state directly.

---

## **Aggregated Metadata**

Dynamic metadata includes:

- Creation, invocation, and completion timestamps
- Execution status and error information
- Aggregated token usage from all descendant Prompts
- Optional trace or diagnostic information depending on runtime support

---

## **Determinism**

Dynamic execution is structurally deterministic.

- Execution behavior is fully determined by the Dynamic definition and control flow.
- Effects are recorded exactly as produced.
- State records outcomes, not execution order or replay instructions.

Variability in model output does not alter execution structure.

## **Dynamic Usage Examples**

### **Example 1: Simple Sequential Dynamic**

```
type: dynamic
name: summarize_text
flow: chain
effects:
  - type: prompt
    name: summarize
    template: "Summarize the following text:\n{{input.text}}"

  - type: prompt
    name: shorten
    template: "Make this summary more concise:\n{{summarize_text.summarize.value}}"
```

---

### **Example 2: Tree-of-Thought Exploration**

```
type: dynamic
name: explore_answers
flow: tot
max_concurrency: 3
effects:
  - type: prompt
    name: angle_a
    template: "Answer optimistically:\n{{input.question}}"

  - type: prompt
    name: angle_b
    template: "Answer critically:\n{{input.question}}"

  - type: prompt
    name: angle_c
    template: "Answer pragmatically:\n{{input.question}}"
```

---

### **Example 3: Nested Dynamic with Control Constructs**

```
type: dynamic
name: iterative_refinement
flow: chain
effects:
  - type: prompt
    name: draft
    template: "Write an initial answer:\n{{input.question}}"

  - type: loop
    name: refine
    max_iters: 5
    until:
      template: "Score >= 0.9"
    body:
      type: dynamic
      name: refinement_step
      flow: chain
      effects:
        - type: prompt
          name: improve
          template: "Improve:\n{{iterative_refinement.draft.value}}"

        - type: prompt
          name: score
          template: "Score quality 0..1:\n{{refinement_step.improve.value}}"
```

---

## **Prime Dynamic**

At the top level of an orchestration file, a Dynamic may be designated as the **Prime Dynamic**:

```
version: 1

prime:
  type: dynamic
  name: main
  flow: chain
  effects:
    - type: prompt
      name: greet
      template: "Hello {{input.user_name}}!"
```

The Prime Dynamic is executed directly by the runtime without requiring a Reflector.

---

## **Conceptual Role**

A Dynamic is a composite effect.

Prompts produce effects.

Conditionals and Loops control execution.

Dynamics compose effects.

Reflectors decide which effects should occur.

Circuitry executes effects and records them to state.

This separation keeps execution deterministic, reasoning explicit, and state fully auditable.
