# Prompt

A **Prompt** is the atomic execution unit in Circuitry and is modeled as a monadic computation.

A Prompt represents **exactly one** model invocation. It transforms state into model input, invokes a model through the runtime’s adapter layer, and records a typed result and execution metadata in runtime state.

Prompts are named and executed within the context of a Dynamic. Prompts do not perform planning, control flow, or iteration.

---

## **Prompt Type**

Every Prompt declares a **Prompt Type**.

The Prompt Type defines:

- how input is materialized
- the expected shape of the output value
- how output is decoded and validated
- how the result is persisted to state

Prompt Types make Prompt results predictable, composable, and safe to interpolate.

---

## **Prompt Object Definition (DOL)**

A Prompt is defined declaratively in the orchestration domain object language.

### **Required Fields**

```
type: prompt        # literal string "prompt"
name: string        # unique within the parent Dynamic
```

A Prompt must also define **exactly one primary input form**:

- template (string), **or**
- messages (structured message array)

---

### **Optional Fields**

```
description?: string    # human- and LLM-readable intent; not executed

# Prompt typing and decoding
prompt_type?: string    # e.g. "text" | "json" | "tool" | "boolean"
schema?: object         # JSON Schema for validating typed output (if applicable)

# Model configuration
model?: string
provider?: string
provider_fallbacks?: string[]

# Model parameters and execution controls
params?: object         # provider-specific (temperature, top_p, seed, etc.)
timeout_ms?: number
deterministic?: boolean

# Input forms
template?: string
messages?:
  - role: string        # e.g. system | user | assistant | tool
    content: string

inputs?: object         # prompt-local structured values
assets?:                # non-text inputs (images, files, etc.)
  - kind: string
    ref: string

# Reliability and error behavior
retries?:
  max_attempts?: number
  backoff_ms?: number | { base_ms: number, max_ms: number, factor?: number }
on_error?: string       # e.g. fail | skip | continue
```

---

### **Validation Rules**

- type must be "prompt".
- name must be unique among sibling nodes.
- Exactly one of template or messages must be present.
- If prompt_type implies structured output, schema should be provided.
- Only one logical model invocation is performed per Prompt.

---

## **Prompt Input and Context**

Prompt input defines what is sent to the model.

Depending on Prompt Type, input may include:

- **template** — a text template rendered against state
- **messages** — structured role-based messages
- **inputs** — structured prompt-local values
- **assets** — non-text inputs such as images or files

When materializing input, **all interpolated values may be sourced from state**.

Prompts render input using a **single effective context** composed of:

- the current state
- inherited values from the parent Dynamic
- prompt-local inputs

All interpolated values are resolved against this effective context using deterministic, nested paths.

Prompts do not manage context merging strategies or scope resolution. Context behavior is consistent across all Prompts.

---

## **Execution Behavior**

Prompts may declare reliability behavior:

- **retries** — retry configuration including maximum attempts and backoff
- **on_error** — error handling policy (fail, skip, continue)

These policies affect execution behavior but do not alter Prompt semantics.

---

## **Monad Semantics**

A Prompt represents a computation of the form:

```
Prompt[T] : State → (State, Result[T])
```

Where:

- **T** is the output type defined by the Prompt Type
- **State** is read-only input and append-only output
- **Result** includes both the produced value and execution metadata

This structure enables predictable composition and consistent execution behavior.

---

## **Execution Lifecycle**

When executed, a Prompt:

1. Builds an effective context from state, inherited values, and prompt-local inputs.
2. Materializes input by rendering templates or messages using values resolved from state.
3. Invokes the model exactly once.
4. Decodes and validates the output.
5. Writes the value and metadata to runtime state.

---

## **State Writes**

A Prompt writes to runtime state under a deterministic path derived from its name and parent Dynamic.

Each Prompt writes:

- **value** — the typed output
- **meta** — execution metadata

Metadata includes timestamps, model and provider information, token usage, retry information, and error details if applicable.

## **Examples**

### **Example 1: Minimal Template Prompt**

```
type: prompt
name: greet_user
template: "Say hello to {{input.user_name}} in one sentence."
```

---

### **Example 2: Typed JSON Prompt**

```
type: prompt
name: extract_entities
description: "Extract key entities from a short paragraph."

prompt_type: json
schema:
  type: object
  properties:
    entities:
      type: array
      items: { type: string }
  required: [entities]
  additionalProperties: false

template: |
  Extract key entities from the following text:
  "{{input.text}}"
```

---

### **Example 3: Messages-Based Prompt**

```
type: prompt
name: summarize_ticket
description: "Summarize a support ticket and suggest a next action."

messages:
  - role: system
    content: "You are a concise support assistant."
  - role: user
    content: |
      Summarize the following ticket and suggest next steps:
      {{input.ticket_body}}
```

---

## **Conceptual Role**

A Prompt is the smallest executable unit in Circuitry.

It is typed, composable, and fully auditable through state. All higher-level behavior in Circuitry emerges from how Prompts are composed into Dynamics and how execution plans are produced.
