# If

> "People can even have conversations with themselves." — Gordon Pask, *Learning Strategies and Learning Styles* (1988)

Everything in Part I is *open-loop*: a static directed graph, every decision made at authoring time. A long chain or a wide tree can run a hundred prompts and still cannot surprise itself, because nothing it produces changes what it does next. What turns it into a *closed-loop* control system is two ideas — **branching on observed state** and **iterating on observed state** — and this chapter is the first.

An `if` is a predicate over state plus two continuations. The interesting case is the model-evaluated predicate: the LLM reads what the run has produced and answers a yes/no question about it. The model becomes the sensor, not just the actuator. A monitor compares, a controller adjusts — the orchestration has begun to observe itself running.

## The shape

```
If        ::= { type: 'if', if: Condition, then: Effect*,
                else?: Effect*, name?: NAME,
                threshold?: NUMBER∈[0,1],                — recorded with model-mode decisions
                on_error?: 'fail'|'skip'|'continue',
                labels?: MAP, description?: STRING }

Condition ::= { mode: 'model', template: TEMPLATE }      — the LLM answers yes/no
            | { mode: 'cel',   expr: CEL,                — deterministic
                strict?: BOOL }                          — default false: an unset path is false
```

`if` and `then` are required. `name` is optional, and whether you give one changes where the branch writes — below.

## Deterministic: `mode: cel`

```yaml
- type: if
  name: check_kind
  if:
    mode: cel
    expr: "'bug' in state.input.labels"
  then:
    - type: prompt
      name: next_step
      template: "Name the first thing to check to reproduce this bug. Issue: {{input.issue}}"
  else:
    - type: prompt
      name: next_step
      template: "Name the docs page that answers this issue, and why. Issue: {{input.issue}}"
```

The expression is evaluated against the shadow state, with `state` bound to its root, in the CEL described in [Shadow state](03-state.md): comparisons, `&& || !`, `?:`, `has()`, the list macros, and the standard functions. It is deterministic — the same state always takes the same branch — and free. Reach for it whenever the decision is already sitting in state as data: a caller input such as the issue's labels, a field of a structured prompt output, a tool's exit code, a loop's termination reason, a complexity score.

An expression that reads an unset path is `false`, not an error, and the runtime logs a warning that names the path. That is convenient for missing paths and treacherous for typos: `'bug' in state.input.lables` quietly takes `else` forever. Read the `branch` recorded on the node when a decision surprises you. When a missing field must not pick a branch — a safety gate, such as the one that opens a pull request only when `state.prime.tests.value.passed` — add `strict: true` beside `mode: cel`. Then an unset path is an error on the `if`, handled by its `on_error`.

An expression that cannot be evaluated at all is always an error. A name CEL does not know, or a function called on the wrong type, is recorded on the node's `meta.error`, and under the default `on_error: fail` the run fails. The branch is never chosen silently.

## Cybernetic: `mode: model`

```yaml
- type: if
  name: review_gate
  if:
    mode: model
    template: "Does this patch fix the problem the issue describes?\n\nIssue: {{{input.issue}}}\n\nPatch:\n{{{prime.patch.value}}}"
  then:
    - type: prompt
      name: verdict
      template: "Summarise in one line what this patch changes:\n{{{prime.patch.value}}}"
  else:
    - type: prompt
      name: verdict
      template: "List what this patch misses.\n\nIssue: {{{input.issue}}}\n\nPatch:\n{{{prime.patch.value}}}"
```

The runtime renders the template, wraps it — *"Evaluate the following condition and respond with ONLY 'yes' or 'no': … Answer (yes/no):"* — and parses the reply leniently: `Yes.`, `yes, because …`, `**TRUE**` and `Y` are true, `No.`/`false!`/`N` are false — a real model rarely answers with a bare token, so surrounding quotes, markdown emphasis and trailing punctuation are stripped before the answer is read. A reply that still doesn't parse as yes/no is not read as false — it **raises**, so `on_error` handles it exactly like a failed model call would; taking `else` for an unreadable answer is only ever the explicit `on_error: continue` opt-in. So phrase the template as a question with a yes/no answer, and put the evidence in it; the model sees only what the template shows.

This is the sensor. The predicate is a judgement no CEL expression could make — *does this patch fix the issue?* — and the model makes it against the run's own output. The cost is one model call and the nondeterminism that comes with it; the return is a control loop that can evaluate quality, relevance, safety, completeness.

`threshold` (default `0.5`) is recorded alongside the decision in `meta`. The built-in evaluator asks for a categorical yes/no, so today the threshold is metadata rather than a cut on a probability; it exists so that an evaluator that returns confidence can honour it without a schema change.

## Named or not

A **named** `if` is a container: its branch effects nest under it — `prime.check_kind.next_step.value` — and the node records the decision:

```
prime.check_kind.value.result        # true / false
prime.check_kind.value.branch        # "then" / "else"
prime.check_kind.value.effects       # what ran
prime.check_kind.meta.mode           # "cel" / "model"
prime.check_kind.meta.condition_result
prime.check_kind.meta.threshold
prime.check_kind.meta.answer         # mode: model only — the raw reply
prime.check_kind.meta.adapter        # mode: model only
prime.check_kind.meta.model          # mode: model only
prime.check_kind.next_step.value     # the branch effect's output
```

An **unnamed** `if` is transparent: it contributes no path segment, and its branch effects write into the enclosing scope as though they were siblings of the `if` itself — `prime.next_step.value`. No decision record is kept. Use the unnamed form when the branching is an implementation detail and downstream just wants `next_step`; use the named form when the decision itself is something you will inspect, branch on again, or cite.

## Same name, both branches

Whichever way the issue went, downstream wants *the next step*. Give the effect the same name in both branches, and every later template reads one path:

```yaml
- type: prompt
  name: reply
  template: "Reply to whoever filed this issue. Thank them and tell them the next step: {{prime.check_kind.next_step.value}}"
```

This is the single most important habit in the chapter. Two branches with different inner names — `reproduce` and `answer` — force every downstream effect to know which branch ran, which is exactly the coupling the `if` was supposed to absorb:

```yaml
# ✗ runtime — downstream cannot address "the next step": one of these two paths is always empty
- type: if
  name: check_kind
  if: {mode: cel, expr: "'bug' in state.input.labels"}
  then:
    - type: prompt
      name: reproduce
      template: "Name the first thing to check to reproduce this bug. Issue: {{input.issue}}"
  else:
    - type: prompt
      name: answer
      template: "Name the docs page that answers this issue, and why. Issue: {{input.issue}}"
- type: prompt
  name: reply
  template: "Reply to whoever filed this issue. Tell them the next step: {{prime.check_kind.reproduce.value}} {{prime.check_kind.answer.value}}"
```

## Inside a branch

A branch is a sequence, and a step in it reads the steps before it. `{{prime.<step>.value}}` inside a branch resolves the branch's own earlier steps first, in templates and in CEL, in a nested `if`, and in an `if` inside a loop body. A named `if` layers its branch over the enclosing scope the way a loop body does, so a branch step shadows a root step with the same name:

```yaml
- type: prompt
  name: next_step
  template: "Name the next step for this issue. Issue: {{input.issue}}"
- type: if
  name: check_kind
  if: {mode: cel, expr: "'bug' in state.input.labels"}
  then:
    - type: prompt
      name: next_step
      template: "Name the first thing to check to reproduce this bug. Issue: {{input.issue}}"
    - type: prompt
      name: reply
      template: "Reply to whoever filed this bug. Tell them the next step: {{prime.next_step.value}}"
```

Inside the `then` branch, `{{prime.next_step.value}}` is the bug's next step. After the `if`, the same spelling is the root `next_step` again, and the branch's is `prime.check_kind.next_step`. The full path works in both places. That is the reason to prefer it: it does not depend on where the template sits.

## Branching on structure

The decisive pattern in Part I was *typed output feeds typed reads*. It pays off here: a `json` prompt produces a field, and a CEL `if` routes on it.

```yaml
- type: prompt
  name: classify
  prompt_type: json
  schema:
    type: object
    properties:
      kind: {type: string}
      confidence: {type: number}
    required: [kind]
  template: |
    Classify this issue as "bug", "feature" or "question".
    Return ONLY a JSON object with "kind" and "confidence".

    {{input.issue}}

- type: if
  name: route
  if:
    mode: cel
    expr: "state.prime.classify.value.kind == 'bug' && state.prime.classify.value.confidence >= 0.7"
  then:
    - type: prompt
      name: plan
      template: "Plan how to reproduce and fix this bug, in at most three steps: {{input.issue}}"
  else:
    - type: prompt
      name: plan
      template: "Plan a reply to this issue that answers the question or states the feature request back to the reporter: {{input.issue}}"
```

Classify-then-route is a bundled pattern (`patterns/classify_then_route`) and a bundled utility (`utilities/route`, which picks one of any number of routes — bug, feature or question — for the branches to test) — [Composition](09-composition.md) shows how to call them rather than restate them.

## Errors on a conditional

`on_error` applies to the *condition*: a model call that fails, a CEL expression that cannot be evaluated, or a `strict` expression that reads an unset path. `fail` propagates. `skip` runs neither branch and records `branch: null`. `continue` takes `else` as a degraded default — the branch you should therefore write as the safe one. A failure *inside* a branch is the branch effect's own business, under its own `on_error`.

## Anti-patterns

**Different names in the two branches.** Above. Same name, always.

**A CEL expression without `state.`** — `'bug' in input.labels` — is legal YAML, passes validation, and fails the run on its first evaluation. Marked in [Shadow state](03-state.md).

**A model condition with no evidence.** "Does the patch fix the issue?" with nothing interpolated asks the model to judge something it cannot see. Put the value in the template.

**Testing for `null`.** `state.prime.related.value == null` is false when the lookup was skipped, because an expression that reads a null path is false as a whole. Test positively for what you need, or test `state.prime.related.meta.error != null`.

**Nesting `if` three deep to express a routing table.** Classify once into a `kind`, then branch once on it — or use `utilities/route` and read the chosen key.
