# If

> "People can even have conversations with themselves." — Gordon Pask, *Learning Strategies and Learning Styles* (1988)

Everything in Part I is *open-loop*: a static directed graph, every decision made at authoring time. A long chain or a wide tree can run a hundred prompts and still cannot surprise itself, because nothing it produces changes what it does next. What turns it into a *closed-loop* control system is two ideas — **branching on observed state** and **iterating on observed state** — and this chapter is the first.

An `if` is a predicate over state plus two continuations. The interesting case is the model-evaluated predicate: the LLM reads what the run has produced and answers a yes/no question about it. The model becomes the sensor, not just the actuator. A monitor compares, a controller adjusts — the orchestration has begun to observe itself running.

## The shape

```
If        ::= { type: 'if', if: Condition, then: Effect*,
                else?: Effect*, name?: NAME,
                threshold?: NUMBER∈[0,1],                — recorded with model-mode decisions
                on_error?: 'fail'|'skip'|'continue',
                labels?: MAP, description?: STRING }

Condition ::= { mode: 'model', template: TEMPLATE }      — the LLM answers yes/no
            | { mode: 'cel',   expr: CEL,                — deterministic
                strict?: BOOL }                          — default false: an unset path is false
```

`if` and `then` are required. `name` is optional, and whether you give one changes where the branch writes — below.

## Deterministic: `mode: cel`

```yaml
- type: if
  name: check_diet
  if:
    mode: cel
    expr: "state.input.diet == 'vegetarian'"
  then:
    - type: prompt
      name: main_course
      template: "Suggest a vegetarian main course for {{input.occasion}}."
  else:
    - type: prompt
      name: main_course
      template: "Suggest a main course for {{input.occasion}}."
```

The expression is evaluated against state with `state` bound to the root, in the CEL described in [State](03-state.md): comparisons, `&& || !`, `?:`, `has()`, the list macros, and the standard functions. It is deterministic — the same state always takes the same branch — and free. Reach for it whenever the decision is already sitting in state as data: a caller input, a field of a structured prompt output, a loop's termination reason, a complexity score.

An expression that reads an unset path is `false`, not an error, and the runtime logs a warning that names the path. That is convenient for missing paths and treacherous for typos: `state.input.deit == 'vegetarian'` quietly takes `else` forever. Read the `branch` recorded on the node when a decision surprises you. When a missing field must not pick a branch — a safety gate, a rule that ends an order — add `strict: true` beside `mode: cel`. Then an unset path is an error on the `if`, handled by its `on_error`.

An expression that cannot be evaluated at all is always an error. A name CEL does not know, or a function called on the wrong type, is recorded on the node's `meta.error`, and under the default `on_error: fail` the run fails. The branch is never chosen silently.

## Cybernetic: `mode: model`

```yaml
- type: if
  name: quality_gate
  if:
    mode: model
    template: "Is this menu balanced and ready to serve?\n\n{{prime.plan_courses.value}}"
  then:
    - type: prompt
      name: verdict
      template: "Approve this menu in one line: {{prime.plan_courses.value}}"
  else:
    - type: prompt
      name: verdict
      template: "Rewrite this menu so it is balanced: {{prime.plan_courses.value}}"
```

The runtime renders the template, wraps it — *"Evaluate the following condition and respond with ONLY 'yes' or 'no': … Answer (yes/no):"* — and parses the reply leniently: `Yes.`, `yes, because …`, `**TRUE**` and `Y` are true, `No.`/`false!`/`N` are false — a real model rarely answers with a bare token, so surrounding quotes, markdown emphasis and trailing punctuation are stripped before the answer is read. A reply that still doesn't parse as yes/no is not read as false — it **raises**, so `on_error` (and any `retries`) handle it exactly like a failed model call would; taking `else` for an unreadable answer is only ever the explicit `on_error: continue` opt-in. So phrase the template as a question with a yes/no answer, and put the evidence in it; the model sees only what the template shows.

This is the sensor. The predicate is a judgement no CEL expression could make — *is this good enough?* — and the model makes it against the run's own output. The cost is one model call and the nondeterminism that comes with it; the return is a control loop that can evaluate quality, relevance, safety, completeness.

`threshold` (default `0.5`) is recorded alongside the decision in `meta`. The built-in evaluator asks for a categorical yes/no, so today the threshold is metadata rather than a cut on a probability; it exists so that an evaluator that returns confidence can honour it without a schema change.

## Named or not

A **named** `if` is a container: its branch effects nest under it — `prime.check_diet.main_course.value` — and the node records the decision:

```
prime.check_diet.value.result        # true / false
prime.check_diet.value.branch        # "then" / "else"
prime.check_diet.value.effects       # what ran
prime.check_diet.meta.mode           # "cel" / "model"
prime.check_diet.meta.condition_result
prime.check_diet.meta.threshold
prime.check_diet.meta.answer         # mode: model only — the raw reply
prime.check_diet.meta.adapter        # mode: model only
prime.check_diet.meta.model          # mode: model only
prime.check_diet.main_course.value   # the branch effect's output
```

An **unnamed** `if` is transparent: it contributes no path segment, and its branch effects write into the enclosing scope as though they were siblings of the `if` itself — `prime.main_course.value`. No decision record is kept. Use the unnamed form when the branching is an implementation detail and downstream just wants `main_course`; use the named form when the decision itself is something you will inspect, branch on again, or cite.

## Same name, both branches

Whichever way dinner went, downstream wants *the main course*. Give the effect the same name in both branches, and every later template reads one path:

```yaml
- type: prompt
  name: wine
  template: "Pick a wine to pair with: {{prime.check_diet.main_course.value}}"
```

This is the single most important habit in the chapter. Two branches with different inner names — `veg_main` and `meat_main` — force every downstream effect to know which branch ran, which is exactly the coupling the `if` was supposed to absorb:

```yaml
# ✗ runtime — downstream cannot address "the main course": one of these two paths is always empty
- type: if
  name: check_diet
  if: {mode: cel, expr: "state.input.diet == 'vegetarian'"}
  then:
    - type: prompt
      name: veg_main
      template: "Suggest a vegetarian main course for {{input.occasion}}."
  else:
    - type: prompt
      name: meat_main
      template: "Suggest a main course for {{input.occasion}}."
- type: prompt
  name: wine
  template: "Pick a wine for {{prime.check_diet.veg_main.value}} {{prime.check_diet.meat_main.value}}"
```

## Inside a branch

A branch is a sequence, and a step in it reads the steps before it. `{{prime.<step>.value}}` inside a branch resolves the branch's own earlier steps first, in templates and in CEL, in a nested `if`, and in an `if` inside a loop body. A named `if` layers its branch over the enclosing scope the way a loop body does, so a branch step shadows a root step with the same name:

```yaml
- type: prompt
  name: main_course
  template: "Suggest a main course for {{input.occasion}}."
- type: if
  name: check_diet
  if: {mode: cel, expr: "state.input.diet == 'vegetarian'"}
  then:
    - type: prompt
      name: main_course
      template: "Suggest a vegetarian main course for {{input.occasion}}."
    - type: prompt
      name: wine
      template: "Pick a wine for {{prime.main_course.value}}."
```

Inside the `then` branch, `{{prime.main_course.value}}` is the vegetarian main course. After the `if`, the same spelling is the root `main_course` again, and the branch's is `prime.check_diet.main_course`. The full path works in both places. That is the reason to prefer it: it does not depend on where the template sits.

## Branching on structure

The decisive pattern in Part I was *typed output feeds typed reads*. It pays off here: a `json` prompt produces a field, and a CEL `if` routes on it.

```yaml
- type: prompt
  name: classify_request
  prompt_type: json
  schema:
    type: object
    properties:
      kind: {type: string}
      confidence: {type: number}
    required: [kind]
  template: |
    Classify this dinner request as "simple" or "elaborate".
    Return ONLY a JSON object with "kind" and "confidence".

    {{input.request}}

- type: if
  name: route
  if:
    mode: cel
    expr: "state.prime.classify_request.value.kind == 'elaborate' && state.prime.classify_request.value.confidence >= 0.7"
  then:
    - type: prompt
      name: plan
      template: "Plan a five-course tasting menu for: {{input.request}}"
  else:
    - type: prompt
      name: plan
      template: "Plan a simple three-course dinner for: {{input.request}}"
```

Classify-then-route is a bundled pattern (`patterns/classify_then_route`) and a bundled utility (`utilities/route`) — [Composition](09-composition.md) shows how to call them rather than restate them.

## Errors on a conditional

`on_error` applies to the *condition*: a model call that fails, a CEL expression that cannot be evaluated, or a `strict` expression that reads an unset path. `fail` propagates. `skip` runs neither branch and records `branch: null`. `continue` takes `else` as a degraded default — the branch you should therefore write as the safe one. A failure *inside* a branch is the branch effect's own business, under its own `on_error`.

## Anti-patterns

**Different names in the two branches.** Above. Same name, always.

**A CEL expression without `state.`** — `input.diet == 'vegetarian'` — is legal YAML, passes validation, and fails the run on its first evaluation. Marked in [State](03-state.md).

**A model condition with no evidence.** "Is the menu good?" with nothing interpolated asks the model to judge something it cannot see. Put the value in the template.

**Testing for `null`.** `state.prime.fetch_recipe.value == null` is false when the fetch was skipped, because an expression that reads a null path is false as a whole. Test positively for what you need, or test `state.prime.fetch_recipe.meta.error != null`.

**Nesting `if` three deep to express a routing table.** Classify once into a `kind`, then branch once on it — or use `utilities/route` and read the chosen key.
