# Complexity — scoring and routing

The system measuring itself. Every prompt in a run has a difficulty — a two-line classification is not a forty-reference audit — and a runtime that can *measure* that difficulty can act on it: send the easy prompt to a small, fast, cheap model and the hard one to a large one, and say afterwards which it chose and why. Circuitry does this with three independent switches, all off by default: **scoring** measures, **routing** chooses a model from the measurement, and [**decomposition**](11-decomposition.md) splits what is too big for any one model to do well.

This chapter is the first two. Nothing in it requires a model call: scoring is deterministic and mechanical, and routing is a table lookup.

## Scoring

With `runtime.complexity.scoring.enabled: true`, every prompt effect is measured on seven signals before it dispatches. Each signal is normalised to `[0, 1]`, multiplied by its weight, and summed; the total is rescaled onto a **0–100** score so that band tables and thresholds are portable between orchestrations whatever their weights.

| Signal | Default weight | Measures |
| --- | --- | --- |
| `prompt_size` | `1.0` | Token estimate of the prompt — the template before a run, the rendered text once state is interpolated. |
| `state_references` | `1.5` | Distinct `{{…}}` references the template reads. |
| `prompt_type` | `0.75` | How structured the expected output is: `boolean`/`number` lowest, `text` in the middle, `json`/`object`/`array` highest. |
| `output_schema` | `1.25` | Depth and field count of a declared schema. |
| `output_size` | `1.0` | Expected output size — a schema's `maxItems`, other declared limits. |
| `structural_position` | `0.5` | Nesting: inside a loop body, inside a conditional branch, generated by a reflector. |
| `keywords` | `1.0` | Whole-word, case-insensitive matches against a keyword → weight table. |

Mechanical signals only. The scorer does not ask a model how hard the prompt is; it counts. That is what makes it free, deterministic, and — because the same seven names are what you configure, what the runtime records, and what the TUI prints — explainable end to end.

```json
{
  "runtime": {
    "complexity": {
      "scoring": {
        "enabled": true,
        "weights": {"state_references": 2.0},
        "keywords": {"audit": 8, "reconcile": 6}
      }
    }
  }
}
```

`weights` overrides only the signals you name; an unknown name is a config error at resolution time, never a silent no-op. `keywords` is the phrase table itself — and its documented default of `{}` is easy to misread as *off*: left unset, a built-in table of reasoning-shaped verbs (`analyze`, `classify`, `compare`, `summarize` …) is active, and a table you supply replaces it.

### What scoring writes

Every scored prompt's node gains `meta.complexity`, written *before* dispatch — so it is on the node when the prompt fails, which is when you most want to know how hard it was, and on a `--dry-run` node too:

```json
"meta": {
  "model": "llama3.1:8b",
  "model_reason": "default",
  "complexity": {
    "score": 34.7,
    "max_score": 100.0,
    "mode": "rendered",
    "signals": {
      "prompt_size": {"raw": 412.0, "normalized": 0.34, "weight": 1.0, "contribution": 4.86, "note": "~412 tokens of rendered prompt"},
      "state_references": {"raw": 3.0, "normalized": 0.3, "weight": 1.5, "contribution": 6.4, "note": "3 distinct references"}
    },
    "warnings": []
  }
}
```

With scoring off there is no `complexity` key at all — not `null`, not `{}` — so a run with the switch off produces the same state tree as a build without the feature. And because `signals` is keyed by name, the score is **addressable from CEL**. An orchestration can branch on how hard its own step was:

```yaml
- type: if
  name: review_depth
  if:
    mode: cel
    expr: "state.prime.plan_courses.meta.complexity.score > 60.0"
  then:
    - type: prompt
      name: review
      template: "Review this menu plan in detail, course by course: {{prime.plan_courses.value}}"
  else:
    - type: prompt
      name: review
      template: "Sanity-check this menu plan in two lines: {{prime.plan_courses.value}}"
```

`cof score` compiles the document and scores each prompt's *template* with no state available — a static preview, no model calls. Five signals are identical either way; `prompt_size` and `keywords` move once real state is interpolated, usually upward. Four kinds of effect cannot be scored at all and are reported as rows with a reason rather than dropped: a `use` (its child is not compiled until it runs), a `tool` (no prompt), a reflector-generated effect (does not exist yet), and an effect a profile disabled. `--json` gives the same table as data.

## Routing

With `routing.enabled: true`, each prompt's score picks a row from an ordered **band table**, and that row's model is what dispatches:

```json
{
  "runtime": {
    "complexity": {
      "scoring": {"enabled": true},
      "routing": {
        "enabled": true,
        "respect_explicit": true,
        "bands": [
          {"name": "light", "max": 20, "model": "phi3:mini"},
          {"name": "mid",   "max": 40, "model": "qwen2.5:7b-instruct"},
          {"name": "heavy",            "model": "gpt-oss:20b"}
        ]
      }
    }
  }
}
```

Bands are ordered; `max` is the band's **inclusive** upper bound (a score of exactly `40` lands in `mid`); the final band omits `max` and is the required **catch-all**, so every score resolves to a model. The table is validated at config resolution — an empty table, a missing or misplaced catch-all, non-ascending bounds, a `max` outside 0–100, an unknown key — all fail before the first effect dispatches, and they fail even when routing is *disabled*, so a broken table surfaces before you flip the switch.

Model names pass through untouched. For a local adapter they are model names; for the CyberDiner broker they are capability tiers (`cheap`, `good`, `alpha`); the router resolves a band to a string and does not interpret it. A band table is also, by itself, a sufficient model configuration: with routing on and no other model set anywhere, the catch-all becomes the run default, and effects that cannot be scored run on it.

### Where the router sits

The router only ever substitutes the **run default**. Anything a human named on purpose beats it:

```
a profile's per-effect model  >  the effect's own model:  >  --model  >  a profile's run-level model:
   >  a profile's per-effect routing pin  >  ROUTER  >  the document's model:  >  config default_model
```

`respect_explicit: true` (the default) is that rule. Set it to `false` and the router decides for *every* scored prompt, including ones that name their own model and runs launched with `--model` — the knob for a cost sweep or a bulk re-run, off by default because overruling a deliberate choice is the surprising behaviour.

A [profile](04-configuration.md) can adjust one effect without touching the table: `routing: false` opts the effect out (it dispatches on the model it would use with routing off entirely), and `routing: heavy` pins it to a named band, bypassing the score. A pin does not need scoring on — it names a model directly — and an explicit `model:` still beats a pin.

### Provenance

A routed effect records who decided:

```
prime.<name>.meta.model            # the model that dispatched
prime.<name>.meta.model_reason     # "router" | "explicit" | "default"
prime.<name>.meta.complexity.band  # {name, model} — the row the score fell in
runtime.effective_settings.sources.model   # "router" when the router won the run
```

`band` is recorded even when the router *defers* — on an effect that pins its own model, or one a profile opted out — answering "what would routing have picked?", which is the question you ask right before removing a pin. `model_reason` is the field that says whether the band was applied; `band` alone never implies it was.

### Watching it happen

```
$ cof run dinner_party.yml --explain-routing -e occasion=anniversary
▸ prime.classify score 7.2/100 · band light · model phi3:mini · why router
▸ prime.plan_courses score 20.5/100 · band mid · model qwen2.5:7b-instruct · why router
▸ prime.audit score 41.7/100 · band heavy · model llama3.1:70b · why explicit
```

One line per prompt effect, printed the moment before it dispatches, read straight off the node's pre-dispatch `meta` — score, band, model, and *why*. The third line is the router deferring: `audit` names its own model and still reports the band it scored into. With scoring off the flag prints nothing; `--quiet` and `--json` suppress it.

`docs/examples/routing/` is a runnable demonstration — one orchestration, two band tables, a pin-and-opt-out profile — that runs under `--dry-run`, because routing happens in the pre-dispatch meta block and no model is ever called.

## Per-run switches and precedence

```bash
cof run dinner_party.yml --scoring --routing              # force both on for this run
cof run dinner_party.yml --no-routing                     # off, whatever config says — beats a profile pin too
cof run dinner_party.yml --scoring --decompose --dry-run  # try decomposition without editing config
```

Each flag flips one `enabled` field; the rest of the sub-block (weights, bands, thresholds) is whatever config or the document already set. The block itself rides the normal `runtime.*` precedence — a document's `runtime.complexity` **replaces** the config's wholesale rather than merging, so a document that overrides it must restate everything it still wants:

```
--scoring/--routing/--decompose  >  orchestration runtime.complexity  >  config runtime.complexity  >  defaults
```

`runtime.effective_settings.sources.complexity` (and `.scoring`, `.routing`, `.decomposition`) records which layer won.

Routing and decomposition each require scoring — enabling either without it is a config error naming the prerequisite — but not each other: score only, score + route, score + decompose, and all three are each valid.

## Anti-patterns

**A table without a catch-all.** Rejected at resolution. Every score needs a model.

**`respect_explicit: false` in a shared config.** It overrules every deliberate `model:` in every document that runs under it. Reserve it for the run where that is the point.

**Reading `band` as "was routed".** `model_reason` is the answer.

**Trusting the static preview as the runtime score.** `cof score` measures templates; the run measures rendered prompts, which pull in whatever state they reference. Use `--explain-routing` on a `--dry-run` to see the rendered numbers before spending anything.

**A document-level `runtime.complexity` that sets one key.** It replaces the whole block; restate the rest.
