# Reflector

A Reflector observes state, applies heuristics or directives, and produces a **Prime Dynamic** to be executed by the runtime. Reflectors do not execute effects, invoke models on behalf of execution, or mutate state directly.

Reflectors are optional. Circuitry does not require a Reflector to begin or continue execution.

---

## **Conceptual Definition**

A Reflector is responsible for:

- reading the current state
- interpreting intent, heuristics, or external signals
- constructing a Prime Dynamic
- deciding whether additional execution should occur

A Reflector defines **what should execute next**, not **how execution occurs**.

---

## **Role in the Architecture**

Reflectors exist *outside* the deterministic execution engine.

They are the only component allowed to:

- decide which Dynamic should run next
- construct new execution plans
- alter future execution topology

They are **never** involved in:

- Prompt execution
- Dynamic execution
- Conditional branching
- Loop iteration

---

## **Reflector Inputs**

A Reflector consumes:

- **State**
    
    The full hierarchical state, including:
    
    - domain state
    - runtime state
    - recorded Effects and metadata
- **Optional Directives**
    
    High-level intent or constraints supplied externally (e.g., user goals, system policies, scheduling hints).
    

Reflectors treat state as read-only input.

---

## **Reflector Outputs**

A Reflector produces one of:

1. **A Prime Dynamic**
    
    A fully-specified Dynamic representing the next execution plan.
    
2. **No output (termination)**
    
    Indicates that no further execution should occur.
    

Reflectors never produce partial plans or executable fragments.

---

## **Prime Dynamic**

A **Prime Dynamic** is a top-level Dynamic produced by a Reflector.

Characteristics:

- has no parent Dynamic
- represents a complete execution unit
- is executed exactly as defined by the runtime
- may contain Prompts, Dynamics, Conditionals, and Loops

A Prime Dynamic is indistinguishable from any other Dynamic once execution begins.

---

## **Reflector Lifecycle**

A typical Reflector lifecycle is:

1. Receive the current state.
2. Inspect relevant domain and runtime information.
3. Apply heuristics, reasoning, or policies.
4. Decide whether execution should continue.
5. If so, construct a Prime Dynamic.
6. Yield the Prime Dynamic to the runtime.
7. Receive updated state after execution.
8. Repeat or terminate.

This cycle is external to the runtime and not visible to execution semantics.

---

## **Iteration**

An **Iteration** represents a single Reflector cycle.

Each Iteration:

- consumes state
- produces at most one Prime Dynamic
- results in zero or one runtime executions
- may record iteration metadata externally

Iterations are **structural**, not executable, and are not represented in the orchestration DSL.

---

## **Reflectors and Determinism**

Reflectors are **not deterministic** by design.

They may:

- invoke models
- apply heuristics
- incorporate external input
- evolve behavior over time

Determinism is preserved because:

- Reflectors do not execute effects
- all execution occurs through explicit Dynamics
- all execution results are recorded in state

This separation keeps planning flexible and execution auditable.

---

## **Reflectors and Cybernetics**

Reflectors may use cybernetic techniques internally (e.g., model-based reasoning), but these are **outside the runtime**.

Cybernetic behavior inside execution is limited to:

- Conditional evaluation
- Loop continuation

Reflector cybernetics do not affect execution semantics directly.

---

## **Reflector Optionality**

Circuitry does **not** require a Reflector.

Valid execution models include:

- executing a single Prime Dynamic directly
- executing a fixed sequence of Prime Dynamics
- interleaving Reflector-driven planning with execution
- disabling Reflectors entirely

This makes Circuitry suitable for both:

- fully deterministic pipelines
- adaptive, long-running systems

---

## **Reflector Constraints**

A Reflector MUST NOT:

- write to state directly
- execute Prompts or Dynamics
- alter execution mid-Dynamic
- observe partial execution results

A Reflector MAY:

- read any part of state
- produce arbitrary Prime Dynamics
- terminate execution explicitly

---

## **Conceptual Role**

A Reflector is a planner, not an executor.

Dynamics describe execution.

Conditionals and Loops control execution.

The runtime executes deterministically.

State records what happened.

Reflectors decide **what should happen next**, while Circuitry ensures that whatever happens is explicit, bounded, and auditable.
