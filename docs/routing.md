# Routing — signals, bands, precedence, and a worked example

This is the field guide for `runtime.complexity`: what the scorer measures,
how to write a band table for your own fleet, where the router sits among
every other way a model gets chosen, and what the whole system is honestly
unable to see. For the field-by-field config schema (types, defaults,
per-run flags, error messages) see [Complexity Configuration](complexity-config.md);
for the static preview command see [`cof score`](score-command.md). This
doc reconciles the two into one reference rather than repeating them —
where it does restate a fact, it is because building a band table needs
that fact right in front of it, not to maintain a second copy.

## The scoring signals

With `runtime.complexity.scoring.enabled: true`, every prompt effect is
measured on seven signals. Each is normalized to `[0, 1]`, multiplied by its
weight, and summed; the total is rescaled onto a **0–100** score so band
tables and thresholds are portable between orchestrations regardless of
their weights.

| Signal | Default weight | Measures |
| --- | --- | --- |
| `prompt_size` | `1.0` | Token estimate of the prompt — the template pre-run, the rendered text once state is interpolated. |
| `state_references` | `1.5` | Distinct state references (`{{...}}`) the template reads. |
| `prompt_type` | `0.75` | How structured the expected output is: `boolean`/`number` score lowest, `text` in the middle, `json`/`object`/`array` highest. |
| `output_schema` | `1.25` | Depth and field count of a declared output schema. |
| `output_size` | `1.0` | Expected output size — a schema's `maxItems`, or another declared limit. |
| `structural_position` | `0.5` | Nesting depth: inside a loop body, inside a conditional branch, generated by a reflector. |
| `keywords` | `1.0` | Whole-word, case-insensitive matches against a keyword → weight table. |

These are the only signal names there are — they are what you write under
`scoring.weights`, what `meta.complexity.signals` reports on every scored
node, and what the TUI's breakdown pane prints, one vocabulary end to end.
An unrecognised name in `weights` is a config error at resolution time, not
a silent no-op (see [Complexity Configuration §scoring](complexity-config.md#scoring)
for the exact message).

### The `keywords` signal has teeth even when you configure nothing

`scoring.weights.keywords` is the *importance* of the keywords signal in the
total score, and defaults to `1.0` like any other weight. `scoring.keywords`
is a separate field — the phrase table itself — and it is easy to read its
documented default of `{}` as "off unless you configure it." In practice it
is not: leaving it unset (or setting it to `{}` explicitly) activates a
built-in table of ~23 reasoning-shaped verbs — `analyze`, `classify`,
`compare`, `critique`, `deduce`, `evaluate`, `extract`, `infer`, `justify`,
`plan`, `prove`, `reason`, `reconcile`, `rewrite`, `summarize`, `synthesize`,
`translate`, `weigh`, and a few multi-word phrases (`chain of thought`,
`cross-reference`, `explain why`, `step by step`) — each pre-weighted by how
much reasoning the verb implies (`rewrite` at `0.05`, `prove` at `0.30`).
There is no config value that fully silences the signal short of naming
`weights.keywords: 0`: an empty table is treated the same as an absent one,
so a template that happens to contain one of those words scores a bit higher
whether you intended a keyword table or not. Set `scoring.keywords` to a
non-empty table of your own to replace the built-in one outright.

Scoring writes its full breakdown to `meta.complexity` on every scored node
— see [What scoring writes to state](complexity-config.md#what-scoring-writes-to-state)
for the shape, and note that the key is written before the effect dispatches
and is entirely absent (not `null`) when scoring is off.

## Band tables

A band table turns a score into a model. It lives at
`runtime.complexity.routing.bands`:

```json
{"name": "cheap", "max": 40, "model": "small"},
{"name": "mid",   "max": 75, "model": "medium"},
{"name": "top",              "model": "large"}
```

- `name` is an optional label, useful for `--explain-routing` output and
  profile pins (below).
- `max` is the band's **inclusive** upper bound. A score matches the
  *first* band in the table whose `max` is greater than or equal to it —
  the boundary condition to remember is that a score of exactly `40` lands
  in a band with `max: 40`, not the next one up.
- A band with no `max` is the **catch-all**. It is required, and it must be
  the last entry, so every score — including one that hits `100.0` — always
  resolves to a model. There is no default catch-all; an omitted one is a
  validation error naming the table, not a silent fallback.

Bands are validated at config resolution — before the first effect
dispatches — whether or not `routing.enabled` is true, so a broken table is
caught the moment it exists rather than the moment it is switched on. The
checks: no empty table, the catch-all present and last, `max` values
strictly ascending (no ties, no gaps that leave a range unreachable, no
overlaps), every `max` numeric and within `0`–`100`, every `model`
non-empty, no unknown keys. `cof score` reads a configured band table even
with routing off, which is the intended way to sanity-check one against real
scores before flipping the switch.

Band names pass through untouched to whatever adapter dispatches the model —
tier names for `cyberdiner`, real model identifiers for local adapters. The
router does not interpret the string, only resolves which one a score
selects.

## The three switches

| Switch | Default | Requires | Turns on |
| --- | --- | --- | --- |
| `scoring` | `false` | — | The deterministic scorer, run on every prompt effect. |
| `routing` | `false` | `scoring` | Band-based model selection from the score. |
| `decomposition` | `false` | `scoring` | Splitting an over-complex effect into chunks (see [Complexity Configuration §decomposition](complexity-config.md#decomposition)). |

**Scoring is the substrate.** Routing and decomposition each consume
scores, so enabling either one without `scoring.enabled: true` fails at
config resolution with a message naming the missing prerequisite — it is
not a warning that lets the run continue unrouted. Routing and decomposition
are otherwise independent of each other: score alone, score + route,
score + decompose, and all three together are all valid combinations.

Per-run flags (`--scoring/--no-scoring`, `--routing/--no-routing`,
`--decompose/--no-decompose`) force one switch for a single `cof run`
without touching any file, and the TUI's launch form offers the same three
switches as tri-state dropdowns. Both are documented in full — including
the flags' own precedence and the `--no-routing`-overrides-a-pin rule — in
[Complexity Configuration §Per-run flags](complexity-config.md#per-run-flags-cof-run---scoringroutingdecompose).

## Precedence

Two separate ladders answer two separate questions: which layer's
*complexity settings* apply, and which *model* a given effect actually
dispatches on. The router only ever answers the second question.

**Settings layer** — where `scoring`/`routing`/`decomposition` and their
sub-fields (weights, bands, threshold, …) come from:

```
--scoring/--routing/--decompose   >   orchestration runtime.complexity   >
config runtime.complexity          >   defaults
```

The merge is shallow: an orchestration-level `complexity` block replaces the
config-level one wholesale, so an override must restate every sub-block it
still wants (see [Complexity Configuration §Precedence](complexity-config.md#precedence)).

**Model chain** — what actually dispatches, and where the router sits in it:

```
profile effect override (model)  >  per-effect model:  >  --model  >
profile effect override (routing pin)  >  ROUTER  >
orchestration model:  >  config default_model
```

Everything above the router is a model a human named on purpose; the router
never overrules one. Everything below it is a default the router exists to
replace. Two things worth stating plainly because they surprise people the
first time:

- **A per-effect `model:` beats `--model`.** This predates routing — an
  effect that names its own model has always opted out of the run default,
  whatever supplied that default. Retarget a specific effect from outside
  the orchestration with a profile's `effects:` block instead.
- **A profile `routing:` pin sits just above the router, not at the top.**
  It beats the router's own score-based choice, but a genuinely explicit
  model — this effect's `model:`, `--model`, or a profile's run-level
  `model:` — still beats the pin. A pin does not need `scoring` enabled: it
  names a band's model directly rather than deriving one from a score. See
  [Per-Effect Routing Control](profiles.md#per-effect-routing-control) for
  the full pin/opt-out mechanics.

The band is recorded at `meta.complexity.band` even on an effect the router
never actually decided — a pinned `model:`, an opted-out profile effect —
so you can always see what routing *would* have picked without removing the
override to find out. `meta.model_reason` is the field that says whether the
band actually applied (`router`) or was deferred to (`explicit`, `default`).

## Worked example

`docs/examples/routing/` has a runnable demo: `triage.yml`, three prompt
effects of deliberately different weight, and two band tables to route them
with. Reproducing it end to end:

```bash
cof score docs/examples/routing/triage.yml --config docs/examples/routing/bands-frugal.json
```

```
                       Circuitry · Score (static preview)
┏━━━━━━━━━━━┳━━━━━━━━┳━━━━━━━┳━━━━━━━━━━┳━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
┃ Effect    ┃ Type   ┃ Score ┃ Band     ┃ Dominant signals / reason            ┃
┡━━━━━━━━━━━╇━━━━━━━━╇━━━━━━━╇━━━━━━━━━━╇━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┩
│ classify  │ prompt │   7.2 │ trivial  │ state_references 4.3                 │
│ summarize │ prompt │  22.0 │ ordinary │ state_references 7.1, prompt_type    │
│           │        │       │          │ 6.4                                  │
│ audit     │ prompt │  43.4 │ hard     │ state_references 10.7, prompt_type   │
│           │        │       │          │ 8.0, output_size 7.9                 │
└───────────┴────────┴───────┴──────────┴───────────────────────────────────────┘
3 scored, 0 not scoreable, 3 effect(s) total.
```

`classify` is one short line reading one state reference; `summarize` adds a
declared object schema; `audit` adds a four-field array schema with a
`maxItems: 20` cap, four state references, and matches the built-in
`keywords` table on "justify" and "reconcile" — three signals compounding
instead of one, which is what pushes a score from "trivial" into "hard"
territory.

### One score, two policies

`docs/examples/routing/bands-frugal.json` and `bands-generous.json` both
turn `scoring` and `routing` on but disagree on where the bands fall:

| Table | trivial | ordinary | hard (catch-all) |
| --- | --- | --- | --- |
| frugal | `max: 10` → `llama3.2:1b` | `max: 30` → `llama3.2` | `llama3.1:8b` |
| generous | `max: 5` → `llama3.2` | `max: 15` → `llama3.1:8b` | `llama3.1:70b` |

```bash
cof run docs/examples/routing/triage.yml --dry-run --explain-routing \
    --config docs/examples/routing/bands-frugal.json \
    -e ticket=... -e rules=... -e prior_decisions=...
```

```
▸ prime.classify score 7.2/100 · band trivial · model llama3.2:1b · why router
▸ prime.summarize score 20.5/100 · band ordinary · model llama3.2 · why router
▸ prime.audit score 41.7/100 · band hard · model llama3.1:70b · why explicit
```

Swap `--config` to `bands-generous.json` and the *same* rendered scores
(7.2, 20.5, 41.7 — routing never changes what gets scored, only what a
score means) land differently: `classify` moves up to `ordinary`
(`llama3.1:8b`) and `summarize` moves up to `hard` (`llama3.1:70b`). One
band table spreads the run across three models; the other pushes most of it
onto two more capable ones. Same orchestration, same scores, different
policy — that is the whole point of the table being config rather than
code.

`audit` reports `why explicit` in both tables: it pins its own
`model: llama3.1:70b` in `triage.yml`, so the router records the `hard` band
it scored into but never substitutes for it. That is the router deferring,
not disagreeing.

### Deferring and pinning

Add `--model llama3.2` to the frugal run and every effect that *was*
routing falls back to the flag — `classify` and `summarize` both report
`why default` at `llama3.2` while `audit` keeps its own pinned model exactly
as before, because a per-effect `model:` outranks `--model` too. The bands
are still computed and still visible; nothing routes.

`docs/examples/routing/profiles/pin-and-opt-out.yml` demonstrates the
profile-level controls over the same demo — `classify: routing: false` opts
it out entirely, `summarize: routing: hard` pins it to the top band
regardless of its own score:

```bash
cof run docs/examples/routing/triage.yml --dry-run --explain-routing \
    --config docs/examples/routing/bands-frugal.json \
    --profile pin-and-opt-out \
    -e ticket=... -e rules=... -e prior_decisions=...
```

```
▸ prime.classify score 7.2/100 · band trivial · model llama3.2 · why default
▸ prime.summarize score 20.5/100 · band hard · model llama3.1:8b · why router
▸ prime.audit score 41.7/100 · band hard · model llama3.1:70b · why explicit
```

`classify` still scores `trivial` — the opt-out doesn't change the score,
only whether the router's answer is used — and dispatches on the
orchestration's own default instead. `summarize` scores `ordinary` on this
table (see the plain frugal run above) but the pin sends it to `hard`
anyway; the band shown is the one that *applied*, not the one the score
alone would have picked. `audit` is unaffected either way, for the same
reason it was unaffected by `--model` above.

## The limits, plainly

### A static preview is not the runtime score

`cof score` compiles the orchestration and scores each prompt's *template*,
without rendering it — no state is available yet, so a `{{...}}` reference
contributes to `state_references` (which just counts distinct references)
but not to `prompt_size` the way real interpolated content would. The
runtime scores the prompt actually sent, after interpolation. Five signals
are identical either way — `output_schema`, `output_size`,
`structural_position`, and `prompt_type` are declared on the effect rather
than measured from content, and `state_references` counts distinct
references regardless of what they resolve to — but `prompt_size` and
`keywords` can move in either direction:

| Effect | Static preview | `--dry-run` rendered (realistic input) |
| --- | --- | --- |
| classify | 7.2 | 7.5 |
| summarize | 22.0 | 20.8 |
| audit | 43.4 | 42.6 |

The common assumption is "runtime is always at least as high, since
interpolation only adds text" — usually true for `prompt_size`, and true
here for `classify`. It is not guaranteed for the total: `summarize` and
`audit` both score *lower* rendered than static, because the `keywords`
signal matches against different text in each mode. `audit`'s template
reads `{{prime.summarize.value}}`; the literal word "summarize" in that
reference matches the built-in keyword table when the raw template is
scored. Under `--dry-run`, `prime.summarize` never actually runs — no
adapter is ever called — so its value is still `null` and the reference
interpolates to nothing, taking that keyword match with it. A real (non-dry)
run would instead substitute `summarize`'s actual output at that point,
which is very likely to push the score *up* past the static preview, as the
general rule expects — the dip is specific to previewing a chain of
not-yet-executed effects with `--dry-run`, not a property of rendering in
general.

Every `cof score` run states the direction of the general rule in its own
footer; treat it as the common case, not a guarantee, when the orchestration
you are estimating chains one scored effect's output into another's prompt.

### Some effects cannot be scored at all — statically or otherwise

A `reflector_generated` effect is planned from its `plan_from_step` prompt's
output at runtime; nothing exists to score before the run reaches it. A
`use` effect's referenced orchestration is not compiled until it executes,
so its children never appear in the frozen tree `cof score` walks. A `tool`
effect calls a plugin, not a model — there is no prompt to measure. And an
effect a `--profile` disabled will not run at all. `cof score` reports all
four as rows with `scoreable: false` and a `reason`, never by omitting them
— an inventory that silently dropped rows would look complete when it
is not. See [`cof score` §What the preview cannot know](score-command.md#what-the-preview-cannot-know)
for the full table and the exact wording each case reports.
